# Sample corpus

The repository is public and MIT licensed, so every document in the sample
corpus is published. Assume a stranger reads all of it, because one will.

This file was the contract for building the corpus and is now also its manifest.
Seventy documents landed on 2026-09-09. The rule below still governs anything
added after that.

## The rule

Every document is either openly licensed with a licence we can name, or
synthetic, written for this purpose and owned by us.

Nothing else qualifies. Specifically:

- No Supabase internal documents. Not a strategy memo, not a roadmap, not a
  Slack export, not an anonymized version of one.
- No customer material of any kind, including material a customer would probably
  be fine with.
- No scraped content of uncertain provenance. A page with no licence statement
  is not openly licensed, it is unlicensed, and unlicensed content does not go in
  a public repository.
- No content generated by pointing a model at a real company's private material.

If the provenance of a file cannot be written in one sentence in the table
below, the file does not go in the corpus.

## The manifest

Seventy documents as of 2026-09-09, one row per file. Every file lives under
`supabase/corpus/` and is listed here. The company, the people and the events
are invented. Alderwick does not exist and none of the people named in the
corpus are real.

`supabase/corpus/COMPANY.md` is the reference the documents are consistent
with: what the fictional company does, who works there, and what it is arguing
about this quarter. Read it before adding a document.

`supabase/corpus/manifest.json` is the machine readable version of this table
and the only thing the loader reads. The markdown files carry no frontmatter,
so a document is a document and its metadata lives in one place.

## What makes a good corpus for this product

The dream job reads a space overnight and writes a digest back into it. If the
corpus is a pile of unrelated public-domain documents, that digest is a list of
summaries and it reads as filler. If the corpus has structure, the same digest
reads as insight, because there was something to work out.

That makes it a writing job rather than a scraping job. The number of documents
matters far less than what is true across them.

Four properties, concretely:

**Overlapping topics across simulated sources.** The same project appears in a
Notion planning document, a Linear issue, a Slack thread and a Drive PDF, each
describing it from that tool's point of view and using slightly different names
for it. The Notion doc calls it the billing migration, Linear calls it
`BIL-204`, Slack calls it "the Stripe thing". Entity extraction has something to
canonicalize, and a search for any of the three finds all four documents.

**A decision that changed.** Something is decided in March, questioned in May,
and reversed in June, with the reasoning present in all three places. This is
what makes the digest worth reading, because a summary that averages the three
is wrong and a summary that orders them is useful. It is also the question a
real knowledge base gets asked most: why did we decide that.

**A thread and an issue about the same thing, never linked.** Two documents from
different simulated sources, high similarity, no explicit reference between
them. This is the entire input to the connections dream kind, and without a
planted pair there is nothing for it to find.

**At least one question whose answer exists only by combining two documents.**
The date is in one, the reason is in the other, and neither alone answers it.
This is the demonstration that retrieval is doing something a file search cannot,
and it is the safest question to ask on stage because its answer is fixed and
verifiable.

Two more things worth planting, since they cost nothing while the corpus is
being written:

- **An exact-match target.** A ticket number, an error code or a version string
  that appears in exactly one chunk. This is the query that proves the lexical
  arm of hybrid search is doing something, described in `docs/retrieval.md`.
- **Dead content.** A handful of documents that are genuinely irrelevant to every
  demo question, so the admin analytics dead-content panel has real rows rather
  than an empty state.

The corpus should also be boring in the right way. It is a fictional company
doing ordinary work: planning, arguing, shipping, changing its mind. No dramatic
incidents, no invented statistics that a viewer might quote, no names close
enough to a real company to be mistaken for one.

## Target shape

Roughly 60 to 80 documents. Enough that search has to discriminate, small enough
that one person can read all of it before a rehearsal and know what a correct
answer looks like.

| Direct upload    | 5 to 10   | Whatever a person drags in. At least one large PDF, for the Edge Function ceiling in `docs/limits.md`. |

Across four spaces in one seeded organization:

| Space                     | Kind     | Contents                                                                                                                    |
| ------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------- |
| Everyone                  | org      | The bulk of the corpus. Product planning, engineering, general company documents. Every member of the seeded org sees this. |
| Engineering               | team     | Technical detail: architecture notes, incident write-ups, the Linear issues.                                                |
| Leadership                | team     | Hiring plans, budget discussion, the compensation review. Two members.                                                      |
| Personal, per seeded user | personal | A few documents each, to prove a personal space stays personal.                                                             |

**The two-user permission demo uses Everyone and Leadership.** Both users are
members of Everyone. Only one is a member of Leadership. They ask the identical
question, one that Leadership content answers more completely, and they get
different answers with no error and no permission dialog on either side.

That pair of spaces has one requirement the rest of the corpus does not: the
Leadership document has to be the obviously better answer to the shared
question, so the difference between the two responses is visible to someone
watching from the back of a room. A difference that only shows up in the
citation list is a correct result and a failed demonstration.

The corpus is seeded through `supabase/seed.sql` and the files themselves live in
the repository, so a fresh clone plus `supabase start` reproduces the demo
without a network call to anything except the embedding model.

`ERR_TRUEUP_4471`.

### Loading it

```
node --env-file=web/.env.local scripts/seed-corpus.mjs --org-slug <slug>
```

`--org-slug` is optional when the database holds exactly one organization. The
script needs `NEXT_PUBLIC_SUPABASE_URL` and `SB_SERVICE_ROLE_KEY`, and the
organization needs at least two members, because two of the five spaces are
personal ones.

It writes a `documents` row, a storage object and a queued `ingest_jobs` row per
manifest entry, and stops there. Chunking and embedding belong to the ingest
worker, so a corpus loaded this way goes through the same pipeline a real Notion
page does. Running it a second time creates nothing, which also keeps every
`updated_at` at its fixed value, since the touch trigger on `documents` rewrites
that column on update.

## Building it

1. Write the fictional company: what it does, who works there, what it is
   arguing about this quarter. One page, so every document afterwards is
   consistent with it.
2. Write the decision that changed, across its three documents, first. It is the
   hardest to get right and everything else is easier once it exists.
3. Write outward from there until the counts in the table are met.
4. Fill in the manifest table above as each file lands, in the same commit as
   the file.
5. Ask the demo questions against the finished corpus and check the answers by
   hand before anything is rehearsed against it. A dream output goes on stage
   only after a person has read it.
